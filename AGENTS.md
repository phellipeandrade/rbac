# AGENTS.md

Repository-specific instructions for Codex and other coding agents working in this project.

## Project purpose

`@rbac/core` (and companion `@rbac/*` workspaces) provides a lightweight hierarchical role-based access-control library for Node.js. It is implemented in TypeScript and publishes CommonJS and ESM entry points, database adapters, framework middlewares, and validation schemas.

Treat authorization correctness, v4 API stability, package interoperability, and predictable performance as core requirements. Prefer small, well-tested changes over broad rewrites.

## Environment and source of truth

- Use Node.js **22.12.0 or later**. The repository pins **22.14.0** in `.nvmrc`; CircleCI also uses Node 22.14.0.
- Use `npm ci` to install the dependencies from the committed lockfile.
- TypeScript is configured in strict mode with an ES2022 target.
- `packages/*/src/` is the source of truth. `packages/*/lib/` is generated by the build; do not edit generated output manually.
- Keep `package-lock.json` in sync when dependencies are intentionally changed.
- Follow the existing formatting and naming conventions. ESLint is configured with the flat config in `eslint.config.mjs`; source code must not introduce explicit `any` types or unused variables.

## Project map

- `packages/core/src/`: named `createRBAC({ roles, ...options })`, `RBACEngine`, `RBACOptions`, permission engine, caches, helpers. Zero runtime dependencies.
- `packages/adapters/src/`: tenant-aware MongoDB, MySQL, PostgreSQL adapters and `createTenantRBAC`.
- `packages/express/src/`, `packages/fastify/src/`, `packages/nestjs/src/`: independent framework bridges.
- `packages/schemas/src/`: Zod-only schema package.
- `scripts/build-entrypoints.mjs`: shared CJS/ESM facades and dual declaration entry points.
- `test/`, `examples/`, `website/docs/`, `README.md`: test and v4 documentation.
- `benchmarks/`: performance baseline and comparisons.

Before changing an area, inspect its implementation, callers, tests, public exports, and relevant documentation.

## Authorization invariants

These behaviors are security-sensitive. Preserve them unless the task explicitly requires a behavior change and the impact is understood:

1. **Deny by default.** Unknown roles and unmatched permissions return `false`. Errors or rejected promises from a `when` predicate must not grant access; preserve the existing fail-closed behavior.
2. **Inheritance is additive.** A role receives permissions from its inherited roles as well as its own definition. Multiple grants that can authorize the same operation combine with OR semantics.
3. **Do not discard conditional grants.** Distinct `when` predicates for the same exact permission or pattern must remain independently evaluable. Do not deduplicate conditional patterns solely because their names or regexes match.
4. **Preserve supported `when` forms.** The API supports boolean values, promises, synchronous/asynchronous predicates, and legacy Node-style callbacks. Prefer the explicit `callbackWhen()` helper for new callback-based code. Do not infer callback behavior from `Function.length`.
5. **Never cache parameter-dependent authorization results.** Permission matching may be cached, but a result that depends on request/user parameters must be evaluated for the current call.
6. **Runtime updates must take effect immediately.** `updateRoles()` merges the supplied role definitions with existing roles, rebuilds the mapped hierarchy, and invalidates relevant permission caches. `addRole()` uses the same update path.
7. **Preserve role-name safety.** Role names that collide with properties inherited from `Object.prototype` must continue to work. Be careful when using ordinary objects as dictionaries; use own-property checks or null-prototype maps where appropriate.
8. **Preserve pattern semantics.** Exact operation names, glob patterns (including the supported `*` and `**` forms), RegExp objects, and slash-delimited regex strings are distinct supported inputs. Reset stateful regexes before repeated tests; global/sticky regexes must not produce alternating results because of `lastIndex`.
9. **Keep caches bounded.** Do not introduce unbounded maps for user-controlled role names, operations, or patterns. Preserve cache invalidation when roles change.

Add regression tests whenever a change touches inheritance, conditional grants, matching, role updates, or caching. Prefer a minimal failing test that captures the reported behavior before modifying the implementation.

## Adapter and tenant-isolation invariants

- Keep all adapters compatible with the `RoleAdapter<P>` interface: `getRoles`, `addRole`, and `updateRoles`.
- Preserve tenant isolation. Every read/write must use the requested tenant identifier; omitted tenant identifiers use the existing `default` tenant behavior.
- Preserve custom column/field mapping through the `columns` option.
- MongoDB, MySQL, and PostgreSQL drivers are optional. Do not turn them into eager imports or mandatory runtime dependencies.
- SQL table and column identifiers cannot be bound as query parameters. Validate identifiers and quote them using the existing dialect-aware utilities. Continue binding all runtime values (role names, serialized role definitions, tenant IDs) as query parameters; never interpolate those values into SQL.
- Preserve schema-qualified SQL table names where supported. Do not weaken identifier validation to make an invalid name pass.
- When changing adapter behavior, cover tenant separation, custom columns, serialization/deserialization, connection reuse/failure behavior, and dialect-specific SQL as applicable.

## Public API and package compatibility

- v4 breaks the v3 curried default factory. Public initialization: `import { createRBAC } from '@rbac/core'`; `createRBAC({roles, enableLogger: false})`.
- Use `RBACEngine`, `RBACOptions`, `Role`, `Roles` and the exported `When` types. No public default factory or v3 alias.
- Import framework integration from `@rbac/express`, `@rbac/fastify`, or `@rbac/nestjs`, adapters from `@rbac/adapters`, validation from `@rbac/schemas`, and optional utilities from `@rbac/core/helpers`.
- CJS and ESM must return identical exported function/class instances. Declarations must typecheck from `.mts` and `.cts` NodeNext consumers. Keep Zod isolated from core.
- Generate all `lib/` files from source; never edit generated code. Always verify packed output. Update `README.md`, current `website/docs/`, examples, tests, and CHANGELOG together for API changes.
- The v4.0 version and `@rbac` package scope changes are specifically authorized by this migration; future releases require explicit instruction. New runtime dependencies require documented justification.

## Middleware contracts

- Keep each integration aligned with its framework contract: Express/Nest middleware uses `next`, the Nest guard implements `canActivate`, and Fastify uses its request/reply pre-handler contract.
- Preserve custom `getRole` and `getParams` extractors and denial handlers.
- Preserve error propagation: Express/Nest middleware forwards caught errors to `next(err)`; do not silently convert infrastructure errors into successful authorization.
- Keep framework integrations structurally typed and avoid adding framework runtime dependencies to the core package.

## Testing and performance expectations

- Add or update tests for every bug fix and behavior change. Put cross-cutting authorization regressions in `test/regressions.spec.ts` when that is the clearest location; otherwise extend the closest existing spec.
- For authorization changes, test both allowed and denied paths, inherited and direct permissions, and conditional predicates with different parameter values.
- For package/export/type changes, run `npm run test:package`; this verifies CommonJS, ESM, shared module identity, subpath exports, lazy Zod loading, and TypeScript consumers.
- For adapter changes, use the existing fake-driver test patterns unless a real database integration test is specifically required.
- For performance changes, run the relevant benchmark before and after on the same environment and compare repeated runs. Benchmarks are environment-dependent: do not claim a universal speedup from a single run or trade correctness for a microbenchmark result.
- Do not rewrite or commit generated files under `benchmarks/results/` unless the task explicitly asks to refresh benchmark artifacts.
- Before considering a code change complete, run the relevant focused tests and, when feasible, the full verification sequence: lint, typecheck, tests, build, package tests, and package dry run. Report commands that were not run; never imply they passed.

## Working process

1. Inspect the current implementation and relevant tests before editing. Confirm the actual behavior rather than assuming the documentation or an earlier implementation is correct.
2. Identify the smallest safe change and the compatibility/security risks.
3. Implement with strict types and existing abstractions. Avoid unrelated refactors, formatting churn, and speculative optimizations.
4. Add regression coverage and update user-facing documentation/changelog when behavior or public usage changes.
5. Run verification appropriate to the change and inspect the final diff for accidental generated files, lockfile churn, or unrelated modifications.
6. In the final report, summarize the change, list validation commands and their actual results, and call out remaining risks or unverified behavior.

Do not run destructive Git commands, rewrite history, commit, push, or publish packages unless the user explicitly asks for that action.
